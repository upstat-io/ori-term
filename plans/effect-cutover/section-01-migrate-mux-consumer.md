11. **`HostEffect::ChildExit` is a ghost variant in production — no emitter today** (new, from Phase 4 reviewer consensus; refined by round-1 TPR finding [TPR-01-1-codex][high]). The variant exists at `oriterm_core/src/effect/families/host.rs:39`, and `LegacyEventSink::push` at `oriterm_core/src/effect/sink/legacy/mod.rs:126` maps it to `Event::ChildExit(code)`, but `grep -rn 'HostEffect::ChildExit\\|Event::ChildExit(' oriterm_core/src/ oriterm_mux/src/pty/ oriterm_mux/src/pane/` returns ZERO production emitters — only the legacy map arm and test-only constructors. Today `MuxEvent::PaneExited` fires only via the dead legacy path. The PTY reader (`oriterm_mux/src/pty/reader/`) detects EOF and closes `byte_tx`, which makes `byte_rx` return `Err` in `PaneIoThread::run` (`oriterm_mux/src/pane/io_thread/mod.rs:141-158, 161-176`) and the thread just returns — **no `MuxEvent::PaneExited` is emitted** in the post-cutover world. **Ownership constraint (verified round 1):** the PTY reader thread does NOT own the child process handle — `PtyHandle` at `oriterm_mux/src/pty/spawn.rs:139-144` holds `child: Box<dyn portable_pty::Child + Send + Sync>` alongside `reader`/`writer`/`control`, and exposes `kill`/`wait`/`try_wait`/`process_id` via the `PtyLifecycle` trait (`spawn.rs:213-228`). `PtyHandle::take_reader` gives the reader thread only a `Box<dyn io::Read + Send>` — the reader cannot call `child.wait()` because it has no reference to `child`. So the naive "reader calls child.wait() on EOF" design does not fit the current ownership model. **Second ownership constraint (verified round 2 [TPR-01-1-codex+gemini][high]):** any watcher thread that takes the `child: Box<dyn Child>` also strands `PtyHandle::kill`/`wait`/`try_wait`/`process_id` (used by `oriterm_mux/src/pane/shutdown.rs:17-23` on pane drop) — you cannot take ownership of `child` from `PtyHandle` AND claim `PtyLifecycle::kill` remains "unchanged" without restructuring `PtyHandle` itself. `portable_pty::Child: ChildKiller` (`crates/portable-pty/src/lib.rs:130,150`) exposes `clone_killer() -> Box<dyn ChildKiller + Send + Sync>` (line 157) that returns a separate killer handle which can `kill()` the child independently of who holds the original `Child`. `process_id(&self)` is also a `&self` method that can be captured before moving the child. **Resolution (corrected design):** restructure `PtyHandle` so kill/signal/wait/try_wait all work AFTER the child is moved to the watcher thread. Concretely: (a) `PtyHandle` fields change: replace `child: Box<dyn portable_pty::Child + Send + Sync>` with `killer: Box<dyn portable_pty::ChildKiller + Send + Sync>` (captured at spawn via `child.clone_killer()` before the child itself is moved) + `process_id: Option<u32>` (captured via `child.process_id()` at spawn time) + `exit_result: Arc<Mutex<Option<Result<ExitStatus, String>>>>` (shared with the watcher thread — using `String` for the error half because `io::Error` is NOT `Clone` per round 2 finding [TPR-01-1-codex-r2][high]; the watcher maps `io::Error` → `err.to_string()` before storing, and `PtyLifecycle::wait`/`try_wait` rehydrate via `io::Error::other(s)` so the outside API still returns `io::Result<ExitStatus>`) + `exit_notifier: Arc<Condvar>` (signal used by `PtyHandle::wait()` consumers to block). (b) `PtyHandle::kill(&mut self)` now calls `self.killer.kill()` — no child needed. `PtyHandle::process_id(&self)` returns `self.process_id`. `PtyHandle::wait(&mut self)` acquires the exit_result mutex and `Condvar::wait`s until `Some(_)` is written, then clones the stored `Result<ExitStatus, String>` (both halves are `Clone`) and maps the `String` error half back to `io::Error::other(s)` before returning `io::Result<ExitStatus>` to the caller. `PtyHandle::try_wait(&mut self)` reads the mutex non-blocking (same rehydration on the error half). (c) A dedicated watcher thread spawned at the same time as the child takes ownership of the full `Box<dyn Child>`, calls `child.wait()` blocking, maps the result to `Result<ExitStatus, String>` via `child.wait().map(ExitStatus::from).map_err(|e| e.to_string())`, writes it into `exit_result`, notifies `exit_notifier` (wakes `PtyHandle::wait()` consumers), AND on success sends `ExitStatus` on a new `child_exit_tx: Sender<ExitStatus>` bounded channel (capacity 1 — child exits once). (d) `spawn_pty` in `oriterm_mux/src/pty/spawn.rs:235-264` changes return shape: returns `(PtyHandle, child_exit_rx: Receiver<ExitStatus>)` so the caller can thread the receiver into `PaneIoThread`'s constructor. ONLY `oriterm_mux/src/domain/local.rs:91` (the `spawn_pty(&pty_config)?` call site) consumes the new tuple — `oriterm_mux/src/domain/handoff/mod.rs` does NOT call `spawn_pty` (confirmed round 2 finding [TPR-01-2-codex-r2][medium]: handoff uses `AdoptedPtyHandle` with its own exit-on-EOF semantics via `AdoptedPtyHandle::wait`). The adopted-pane path wires a separate channel: `AdoptedPtyHandle::deliver_exit` (called when the reader observes EOF — see `handoff/mod.rs:68-70`) sends `ExitStatus::synthesized_eof()` (`spawn.rs:56`) on a `child_exit_tx: Sender<ExitStatus>` bounded channel, whose `child_exit_rx` half is threaded into the adopted pane's `IoThreadConfig` at `handoff/mod.rs:141`. This keeps one uniform `PaneIoThread` interface across local + adopted panes without making either path fake an unused channel. (e) `PaneIoThread` gains `child_exit_rx: Receiver<ExitStatus>` as a new field alongside `byte_rx`/`cmd_rx`. Both `select!` blocks in `run()` (lines 141-158 and 161-176) add a `recv(self.child_exit_rx) -> status => { ... }` arm that pushes `Effect::Host(HostEffect::ChildExit { code: status.exit_code() as i32 })`, calls `self.drain_effects_into_mux_events()` to flush, then `return;`s. (f) **Exit-code capture is deterministic, not racy** (round 2 finding [TPR-01-1-gemini-r2][high]): when `byte_rx.recv()` returns `Err(_)` (PTY stream closed — child has exited or is about to), the IO thread enters a "draining" state rather than exiting immediately. It performs: (i) a final `self.drain_effects_into_mux_events()` to flush any in-flight effects from the last parse chunk; (ii) a blocking `self.child_exit_rx.recv_timeout(Duration::from_secs(5))` — 5s is a generous upper bound that accommodates scheduler jitter and signal-delivery delays on loaded systems; empirically `child.wait()` returns within <100ms of EOF on Linux / macOS / Windows when the child has actually exited. (iii) On `Ok(status)`: emit `HostEffect::ChildExit { code: status.exit_code() as i32 }`, drain once more, return. (iv) On `Err(RecvTimeoutError::Timeout)` or `Err(RecvTimeoutError::Disconnected)`: log an error (`log::error!("PaneIoThread: child exit not observed within 5s after EOF; emitting ChildExit {{ code: 0 }} as fallback")`), emit `HostEffect::ChildExit { code: 0 }`, drain once more, return. The 5s upper bound bounds shutdown latency while still being deterministic under normal operation — the previous 50ms was too tight (scheduling jitter on a loaded Windows/Linux system can exceed 50ms routinely). Pin: `pty_eof_exit_code_captured_after_scheduler_delay` — inject a 200ms delay between PTY EOF and watcher `child.wait()` return via a mock; assert `MuxEvent::PaneExited { exit_code: <injected_code> }` (not 0). (g) The existing tests at `oriterm_mux/src/pty/adopt/tests.rs:81-155` (`pty_lifecycle_kill_is_no_op`, `pty_lifecycle_try_wait_returns_*`, `pty_lifecycle_wait_blocks_until_signal_then_unblocks`) MUST still pass — they test `AdoptedPtyHandle`, which is unaffected by this change. `PtyHandle::wait` (separate impl, used by `pane/shutdown.rs:23`) now blocks on `exit_notifier` via the watcher thread instead of blocking inside the child directly, but the observable behavior is identical. (h) No daemon / serialization impact: the watcher + channel are entirely process-local; daemon-mode child-exit is already tracked separately. This restructure is the SSOT-correct way to split ownership: the `Child` trait object has exactly ONE owner (the watcher), the killer has exactly ONE owner (PtyHandle via the cloned killer), process_id is captured at spawn (not re-queried), and wait/try_wait consumers block on a canonical exit-status cell. Pinned by semantic test `pty_eof_emits_pane_exited_via_effect_router` in `effect_router/tests.rs` — construct `PaneIoThread<QueueingEffectSink>` with a mock `byte_rx` that sends `Ok(b"x".to_vec())` then drops its sender, and a mock `child_exit_rx` that forwards `ExitStatus { code: 42, signal: None }` before dropping; assert `mux_rx.recv_timeout(5s)` returns `MuxEvent::PaneExited { pane_id, exit_code: 42 }`. Companion negative pin `pty_eof_without_exit_code_defaults_to_zero` — drop `child_exit_tx` without sending; assert `MuxEvent::PaneExited { exit_code: 0 }` after the 50ms fallback. This is NOT deferrable to 01.3 — deletion without a real emitter is a user-visible regression (panes appear to "hang" after the shell exits; the UI never knows to close them).
12. **`ResponseToken<T>::fulfill()` is last-write-wins — duplicate fulfillment silently overwrites** (new, from Phase 4 architectural-risk §1). `oriterm_core/src/effect/families/host_request.rs:69-71` does `*self.slot.lock() = Some(value)` unconditionally — a second `fulfill()` call silently replaces the first value; the first `take()` sees whichever write landed last. Because `ResponseToken<T>: Clone` (`host_request.rs:53`), a token can be cloned into BOTH `register_host_request_response` (IO-thread pending poll) AND `MuxEvent::HostClipboardLoad::reply` (main-thread fulfill path) — if a future consumer accidentally fulfills from two sites (e.g. an overlay widget AND the main clipboard handler race), the duplicate fulfill is undetectable. **Resolution:** 01.2 adds single-assignment semantics to `ResponseToken<T>::fulfill` — the method becomes `pub fn fulfill(&self, value: T) -> Result<(), AlreadyFulfilled>` returning `Err` if the slot is already `Some(_)`. 13. **`PendingResponse` leaks forever if consumer drops its handle unfulfilled** (new, from Phase 4 blind-spot §4; unified round-4 [TPR-01-3-codex-r4][medium] — single cancellation design). `oriterm_mux/src/pane/io_thread/response_poll.rs:48-55, 64-71` moves the `ResponseToken<T>` into a `Box<dyn FnMut() -> Option<Effect>>` closure captured inside `PendingResponse`. The closure holds an `Arc<Mutex<Option<T>>>` via the token. If the main-thread consumer (e.g. the clipboard handler) drops its `MuxEvent::HostClipboardLoad::reply` handle WITHOUT calling `fulfill_clipboard_load` (user dismisses a permission prompt, overlay closes, pane closes mid-request), the IO thread's `pending_responses` entry keeps the token's `Arc` alive forever — `poll_pending_responses()` polls it every tick and `reply.take()` always returns `None`. The `pending_responses: Vec<PendingResponse>` grows unboundedly under this pattern (violates RSS invariant, violates the wake-channel collapse semantic). **Resolution (unified Arc-only design — no Weak):** 01.2 adds cancellation detection via `Arc::strong_count`. `PendingResponse` stores a clone of the token's `slot: Arc<Mutex<Option<T>>>` (captured at registration); the main-thread-facing `ResponseToken<T>` holds another `Arc` clone. When both are live, `Arc::strong_count(&self.slot) == 2` (one pending + one consumer). When the consumer drops the handle, `Arc::strong_count(&self.slot) == 1` (only the IO-thread pending holds it). `PendingResponse::poll` checks `Arc::strong_count(&self.slot) <= 1` AFTER calling `take()` returns `None` — if the consumer side is gone AND the slot is still empty, the entry is cancelled (returns `PollResult::Cancelled`) and `poll_pending_responses()` removes it from the vector WITHOUT pushing a PTY write. No `Weak` reference is used — the pending's own Arc is what keeps the slot alive across the `take()` call, and strong_count discriminates consumer-dropped from still-live based on whether the MAIN-thread Arc exists. Pinned by `pending_response_cancelled_when_consumer_handle_dropped` in `response_poll/tests.rs` — register a host request, drop the main-thread `reply` handle, run `poll_pending_responses()` twice, assert `t.pending_responses.is_empty()` AFTER the second call (the two-tick delay handles the race where the consumer hasn't dropped yet at the moment of registration) and NO `MuxEvent::PtyWrite` was emitted. Bounded by `debug_assert!(self.pending_responses.len() < MAX_PENDING_RESPONSES = 64)` so even a detection bug surfaces before production runs blow RSS. This design lives in `oriterm_core` alongside `PendingResponse`/`ResponseToken`/`PollResult` — the `oriterm_mux`-side `poll_pending_responses` consumes the `PollResult` variants but does not own the cancellation logic (SSOT: detection policy is in `oriterm_core`).

15. **`PtyEffect::Write { bytes: Vec<u8> }` → `MuxEvent::PtyWrite { data: String }` is a lossy boundary** (new, from Phase 4 architectural-risk §2). Pinned by `pty_write_preserves_non_utf8_bytes` in `effect_router/tests.rs` — push `PtyEffect::Write { bytes: vec![0x90, 0xFF, 0x00, 0x80] }`, drain, assert `mux_rx.recv()` yields `MuxEvent::PtyWrite { data: vec![0x90, 0xFF, 0x00, 0x80] }` byte-exact (not `String::from_utf8_lossy`'d). **This change has blast radius — it's why 01.1's cross-crate commit is large, not a reason to skip it.**
16. **Router wakeup omission would silently starve the main-thread event loop** (new, from Phase 4 blind-spot §1). Today `IoThreadEventProxy::send` at `oriterm_mux/src/pane/io_thread/event_proxy/mod.rs:68-71` calls `(self.wakeup)()` after every `mux_tx.send(event)` so the winit event loop observes the newly queued `MuxEvent` via the app-waker callback (`IoThreadConfig.wakeup: Arc<dyn Fn() + Send + Sync>` at `handle.rs:98`, held as `PaneIoThread.wakeup` after `new_with_handle` at `handle.rs:139`). The `UiEffect::CursorBlinkChanged` + `UiEffect::MouseCursorDirty` arms ALSO call `(self.wakeup)()` at `event_proxy/mod.rs:150-152`, and `pump_mux_events()` at `oriterm_mux/src/in_process/event_pump.rs:33-44` is only entered when the waker fires. If the new `effect_router::drain_effects_into_mux_events()` forgets to call `(self.wakeup)()` after pushing to `mux_tx`, `pump_mux_events()` never fires and the app never observes the metadata event — no compile error guards this; the regression is runtime-only. **Resolution:** 01.1 documents the wakeup contract on `drain_effects_into_mux_events` and wraps the `mux_tx.send` + `(self.wakeup)()` pair in a single private helper `send_mux_event(&self, event: MuxEvent)` on `PaneIoThread<QueueingEffectSink>` — every arm of the router goes through this helper, never direct `self.mux_tx.send`. The helper also fires `(self.wakeup)()` for the no-MuxEvent variants (`UiEffect::CursorBlinkChanged`, `UiEffect::MouseCursorDirty`) to preserve the legacy semantics at `event_proxy/mod.rs:150-152`. Pinned by `router_fires_wakeup_after_every_mux_event` in `effect_router/tests.rs` — inject a counting `wakeup: Arc<AtomicU64>` closure, push N effects that each map to a MuxEvent, drain, assert `wakeup_count.load() == N`. Companion `router_fires_wakeup_for_ui_effects_without_mux_event` — push one `UiEffect::CursorBlinkChanged` + one `UiEffect::MouseCursorDirty`, drain, assert `wakeup_count.load() == 2` AND `mux_rx.try_recv().is_err()`.
17. **Trailing output loss on process exit — final snapshot must land before `MuxEvent::PaneExited`** (new, from Phase 4 blind-spot §2 / architectural-risk §3). Today the `byte_rx.recv()` EOF branch in `PaneIoThread::run` causes an immediate thread return (`oriterm_mux/src/pane/io_thread/mod.rs:151-154`). After 01.1 lands the `HostEffect::ChildExit` draining sequence (blind-spot §11), the steps are: (i) final `drain_effects_into_mux_events()` to flush last-chunk effects, (ii) `child_exit_rx.recv_timeout(5s)`, (iii) push `HostEffect::ChildExit`, (iv) drain again, (v) return. That sequence still **misses the final snapshot** — the main thread's last-observed snapshot is whatever was current when EOF arrived, NOT the snapshot reflecting the last parse chunk (e.g. the shell's final prompt line, a goodbye banner, or the exit-code-sourced status line). `post_parse_housekeeping` (called at the end of `handle_bytes` per the current `mod.rs:260-283` flow) produces the snapshot via the `SnapshotDoubleBuffer::flip_swap()` path — but between the last `handle_bytes` and the EOF, no `post_parse_housekeeping` call happens. **Resolution:** 01.1's EOF-draining sequence inserts an explicit `self.post_parse_housekeeping()` + snapshot `flip_swap()` call BEFORE pushing `HostEffect::ChildExit`, guaranteeing the final snapshot reflects everything the PTY wrote right up to EOF. Ordering: (i) final `drain_effects_into_mux_events()`, (ii) `post_parse_housekeeping()` (snapshot flip), (iii) `child_exit_rx.recv_timeout(5s)`, (iv) push `HostEffect::ChildExit { code }`, (v) `drain_effects_into_mux_events()` (emits `MuxEvent::PaneExited`), (vi) `return;`. This guarantees the main thread sees `[final-snapshot, MuxEvent::PaneExited]` in that order, never the reverse. Pinned by `final_snapshot_precedes_pane_exited` in `effect_router/tests.rs` — seed a PTY with bytes that produce a distinctive last-line cell content, close `byte_tx`, forward an exit code on `child_exit_tx`, assert the main thread's `SnapshotDoubleBuffer::swap_front()` observes the distinctive cell content AND `mux_rx.recv_timeout(5s)` yields `MuxEvent::PaneExited` with `exit_code` matching the forwarded status AND the snapshot was observed BEFORE the PaneExited event (use a shared `Vec<Observation>` timeline to assert ordering). Without this pin, panes that emit a final banner + exit (e.g. `echo bye; exit 1`) would lose the banner on the main thread's display.
18. **Move-only ownership invariant for `ResponseToken` across staging buffers** (new, from Phase 4 blind-spot §3 / architectural-risk §5). The Arc-strong_count cancellation design at blind-spot §13 discriminates "consumer alive" (strong_count == 2) from "consumer dropped" (strong_count == 1) based on the assumption that exactly ONE `Arc<Mutex<Option<T>>>` clone lives outside the `PendingResponse`. Multi-stage staging buffers defeat this assumption: the daemon client at `oriterm_mux/src/backend/client/mod.rs:46-47` buffers `notifications: Vec<MuxNotification>`; the daemon server at `oriterm_mux/src/server/mod.rs:94` holds `notification_buf: Vec<MuxNotification>`; `oriterm/src/app/mux_pump/mod.rs:44` drains through `with_drained_notifications()`; `oriterm/src/app/window_management/mod.rs:212-230` stages further. Every `MuxNotification::HostClipboardLoad { reply: ResponseToken<String>, .. }` push into one of these buffers adds an Arc clone, pushing `Arc::strong_count` from 2 to 3 (or 4, or N) and making `PendingResponse::poll` see a still-live consumer long after the main-thread handler already logically dropped its reply handle. Cancellation detection becomes unreachable until every staging buffer drains. **Resolution:** 01.1 documents a **move-only ownership invariant** for `ResponseToken`: every staging-buffer site MUST take ownership by `mem::replace` / `Vec::drain` / match-move, never `.clone()` of the `MuxNotification` variant that carries a token. The invariant is enforced by (a) a doc-comment on `ResponseToken<T>` at `oriterm_core/src/effect/families/host_request/mod.rs` (post-01.2 directory-module split) stating "Move-only across staging buffers. Cloning a `ResponseToken` into a persistent buffer defeats `Arc::strong_count`-based cancellation detection in `PendingResponse::poll`. Clone is provided ONLY for the single IO-thread register + main-thread reply handoff — ALL downstream buffers MUST move, not clone."; (b) a `#[test]` `host_clipboard_load_notification_is_not_clone_from_buffer` that uses a compile-fail / grep assertion — runtime `include_str!`s for `notifications.push(notif.clone())` and `notification_buf.push(n.clone())` across `oriterm_mux/src/backend/client/`, `oriterm_mux/src/server/`, `oriterm/src/app/mux_pump/`, `oriterm/src/app/window_management/` return zero hits; (c) a semantic pin `cancellation_detects_after_staging_drain` in `response_poll/tests.rs` — register a `HostClipboardLoad`, simulate ONE staging-buffer hop via `Vec::drain` (move, not clone), drop the reply at the far side, call `poll_pending_responses()` twice, assert `pending_responses.is_empty()` — proves cancellation still detects with one staging hop; companion negative `cancellation_fails_when_buffer_clones_token` — deliberately clone the notification into a buffer, drop one side, assert cancellation does NOT trigger (documents the trap and serves as a guard that future staging buffers don't regress to cloning). The SSOT for the invariant lives on `ResponseToken`'s doc comment; consumers inherit it via the doc + the grep pin.

## Architectural Context (read before implementing)

Current state (verified against code at the time of this review):

- IO thread's `Term<S>` type parameter is `S: EffectSink + 'static`. Today `S = LegacyEventSink<IoThreadEventProxy>`. Construction sites: `oriterm_mux/src/domain/local.rs:139-145` and `oriterm_mux/src/domain/handoff/mod.rs:116-122` both call `Term::new(.., LegacyEventSink::new(IoThreadEventProxy::new(..)))`.

## 01.4 Daemon-mode IPC for `HostRequest` — design + bug filing + follow-up plan

**Goal:** Resolve the daemon-mode IPC incompatibility surfaced in blind-spot §2 and architectural-risk §1. `ResponseToken<T>` is `Arc<Mutex<Option<T>>>` (`oriterm_core/src/effect/families/host_request/mod.rs` post the 01.2 directory-module split; pre-01.2 it lives at `oriterm_core/src/effect/families/host_request.rs:54-56`) — process-local only. `oriterm_mux/src/protocol/messages.rs:396-401` (`NotifyClipboardLoad`) today serializes only `pane_id: PaneId` + `clipboard_type: u8`; there is no request-ID and no reply PDU. As a result, daemon-mode OSC 52 load (`\x1b]52;c;?\x1b\\`) CANNOT round-trip through the IPC transport even after 01.3 lands.

This subsection has three exit paths; it is **mandatory** — not skippable. Choose one path and execute it end-to-end.

**Path A — In-scope design (recommended when daemon-mode is part of the next release):**
- [ ] Add `NotifyHostRequest { pane_id, request_id: u64, payload: HostRequestPayload }` to `oriterm_mux/src/protocol/messages.rs` (wire variant). `HostRequestPayload` is the serialize-safe projection of `HostRequest` — drops `ResponseToken`, carries enough context to rebuild the reply.
- [ ] Add `ReplyHostRequest { request_id: u64, payload: HostReplyPayload }` as the paired reply PDU.
- [ ] Server side (daemon) stores an in-memory `HashMap<u64, PendingDaemonReply>` keyed by `request_id`, where `PendingDaemonReply` is a NEW erased enum `enum PendingDaemonReply { ClipboardLoad(ResponseToken<String>), ColorQuery(ResponseToken<Rgb>) }` defined in `oriterm_mux/src/server/pending_replies.rs` (new file). Round-6 finding [TPR-01-11-codex][medium]: a naked `HashMap<u64, ResponseToken<...>>` is non-compilable because `ResponseToken<String>` and `ResponseToken<Rgb>` are different concrete types; the placeholder `<...>` hid the same erasure-vs-typed design flaw that round-0 caught on `PendingResponse` (see [TPR-01-5-codex]). Incoming `ReplyHostRequest` matches on `PendingDaemonReply::ClipboardLoad` / `::ColorQuery` to fulfill the correct token via `token.fulfill(value)?`, removes the entry from the map, and signals the wake channel introduced in 01.2. Alternative design: type-erased via `Box<dyn PendingReply>` trait object (slightly more flexible for future `HostRequest` additions) — the enum form is preferred for the initial landing because the variant set is small and closed, and exhaustive match at the fulfill site prevents silent-drop drift. The `PendingDaemonReply` type lives in `oriterm_mux/src/server/` because the daemon server is the sole owner of this cross-process reply mapping; it is NOT hoisted to `oriterm_core` (no other crate needs it).
