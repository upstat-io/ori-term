# Section 01: Migrate Mux Consumer

## Mission-Criterion Connection

This section's mission criteria trace upward to `00-overview.md §Goal`:

- "Migrate `oriterm_mux` IO thread from `LegacyEventSink` → `QueueingEffectSink`" → delivered atomically by 01.1 (sink swap + router land in a single commit; no intermediate state silently drops effects).
- "Delete `LegacyEventSink`, `Event::ClipboardLoad`, `Event::ColorRequest`" → delivered by 01.3.
- "Remove the `drain_notifications()` thin shim" → delivered by 01.3.
- "All consumers process effects via `drain_into()` — no separate notification drain" → delivered by 01.1 + 01.3.
- "Add an idle-wake channel so a fulfilled `ResponseToken` unblocks the IO thread's `crossbeam_channel::select!`" → delivered by 01.2.

Downward: this section also unblocks `plans/spec-conformance/section-10-osc-suite.md` success criterion 7 (line 14) — Section 10.2's removal of the `#[allow(dead_code)]` gate on `register_host_request_response` is no-op once this section lands because this section wires the live call site AND removes the gate. Section 10.2 will only need to write the round-trip `#[test]` against the already-activated path.

## Blind Spots (reviewer-surfaced — MUST be resolved in this section, not deferred)

Both `codex` and `gemini` reviewers raised these during `/review-plan` Phase 4. Each resolves inside a named subsection below — none is deferred.

1. **Atomicity of sink swap + router** — 01.1 as a standalone landable commit silently drops all effects (bells, title, CWD, clipboard requests). `oriterm_mux/src/domain/local.rs:130` and `domain/handoff/mod.rs:106` construct panes whose `QueueingEffectSink` has no drain caller yet. **Resolution:** merged into a single atomic 01.1 subsection covering BOTH sink swap AND router activation AND wake channel wiring of the drain call sites. There is no intermediate commit where effects queue without being drained.
2. **Daemon-mode IPC incompatibility** — `ResponseToken<T>` is `Arc<Mutex<Option<T>>>` (`oriterm_core/src/effect/families/host_request.rs:54-56`) — process-local, cannot cross IPC. `NotifyClipboardLoad` in `oriterm_mux/src/protocol/messages.rs:396-401` serializes only `pane_id` + `clipboard_type`, not a token. **Resolution:** 01.4 is dedicated to the daemon-mode audit: either adds a request-ID + reply-PDU design in-scope, or files a `/add-bug` artifact with a concrete repro-and-fix plan, or cross-links to a new plan. No silent deferral.
3. **`Event::ChildExit` dual-path ambiguity** — Emitted and matched in `event_proxy/mod.rs:143-148` AND `mux_event/mod.rs:245`. After 01.3's `IoThreadEventProxy` deletion, the effect-based path must absorb the child-exit signal. **Resolution:** 01.1 Cleanup block mandates a grep + documentation step naming every `Event::ChildExit` producer and consumer. If the reader thread still emits `Event::ChildExit` via `MuxEventProxy`, the plan documents whether that path survives or is migrated — before 01.3 touches the deletion set.
4. **Router under-exercise via `VoidEffectSink`** — The dominant test helpers at `oriterm_mux/src/pane/io_thread/tests.rs:13` (`make_sync_thread`) and `:54` (`make_sync_thread_generic`) use `VoidEffectSink`; `QueueingEffectSink` coverage is concentrated at `tests.rs:1927`. **Resolution:** 01.1 introduces `make_sync_thread_queueing()` AND migrates existing test helpers where the production code path they cover now runs through the router. No router variant relies solely on a `VoidEffectSink` helper.
5. **Unbounded effect accumulation across parse chunks** — `handle_bytes_chunked` at `oriterm_mux/src/pane/io_thread/mod.rs:220-234` invokes `handle_bytes` per `MAX_PARSE_CHUNK` (64 KB) slice. If the drain only fires at the end of `handle_bytes_chunked` (or only at `run()` loop top), a 1 MB forwarded read accumulates effects in the sink. **Resolution:** 01.1 places the drain call at the end of `handle_bytes`, NOT at the end of `handle_bytes_chunked` — every 64 KB slice drains its effects before the next slice enters. Pinned by `multi_chunk_parse_drains_between_chunks`.
6. **`MuxEventProxy` lifecycle** — `mux_event/mod.rs:137-257` implements `EventListener` for a now-dead IO-thread path; `mux_event/tests.rs:11,15,25,…` still references it. **Resolution:** 01.3 runs the audit; if unused in production, the struct + impl + tests are deleted; if still used, a deprecation bug is filed.
7. **Sync→async ordering change** — `DesktopNotification`, `ClearPendingNotifications`, title, CWD, bell effects today fire synchronously at VTE-byte time via `LegacyEventSink::push`. Post-migration they fire at "next drain" (end of `handle_bytes`). **Resolution:** because the drain runs at the same `handle_bytes` boundary (lines 260-283) that already exists between the byte processor and `post_parse_housekeeping`, observable ordering is preserved to the main thread (snapshot production happens AFTER `post_parse_housekeeping`, which runs AFTER the drain). Pinned by `drain_preserves_push_order_end_to_end`. If any existing timing-sensitive integration test relies on metadata-before-snapshot ordering, it must still pass — validated by running the full suite at every subsection boundary.
8. **`HostEffect::{VisualBell, AudioRequest, PrintRequest}` are functional regressions from day 1 if only logged** — real `\a` sequences fire these. **Resolution:** 01.1's Cleanup block files `/add-bug` artifacts for each (severity medium) that enumerate the concrete user-facing regression (audible bell not forwarded, print request dropped, visual-bell not driving UI flash). The bug artifact IS the resolution; leaving them as log-only is acceptable ONLY because the bug artifact tracks the user-visible gap for a separate fix.
9. **Cross-crate consumer exhaustive-match coupling** — adding `MuxEvent::DesktopNotification`, `MuxEvent::HostClipboardLoad`, `MuxEvent::HostColorQuery` and `MuxNotification::{DesktopNotification, ClearPendingDesktopNotifications}` forces exhaustive-match updates in `oriterm/src/app/**`. **Resolution:** 01.1 Files block enumerates each exhaustive-match site (via `grep -rn 'match.*MuxNotification\|match.*MuxEvent' oriterm/src/`) — every site is covered by an embedded checklist item, not a vague "update callers". Concrete enumeration happens in implementation; placeholder here.
10. **`oriterm/src/app/window_management/mod.rs:214` and `oriterm/src/app/mux_pump/mod.rs:44` call `mux.drain_notifications(&mut self.notification_buf)`** — this is the mux's `InProcessMux::drain_notifications` at `oriterm_mux/src/in_process/event_pump.rs:102`, which is DIFFERENT from the `Term::drain_notifications()` shim at `oriterm_core/src/term/shell_state/mod.rs:356` that 01.3 deletes. **Resolution:** 01.3 explicitly preserves `InProcessMux::drain_notifications` (it still drains `MuxNotification`s from the mux) and deletes ONLY the `Term` shim. Documented by the `no_drain_notifications_shim` pin which narrows its grep to `oriterm_core/src/term/`.

The PTY reader (`oriterm_mux/src/pty/reader/`) detects EOF and closes `byte_tx`, which makes `byte_rx` return `Err` in `PaneIoThread::run` (`oriterm_mux/src/pane/io_thread/mod.rs:141-158, 161-176`) and the thread just returns — **no `MuxEvent::PaneExited` is emitted** in the post-cutover world. **Ownership constraint (verified round 1):** the PTY reader thread does NOT own the child process handle — `PtyHandle` at `oriterm_mux/src/pty/spawn.rs:139-144` holds `child: Box<dyn portable_pty::Child + Send + Sync>` alongside `reader`/`writer`/`control`, and exposes `kill`/`wait`/`try_wait`/`process_id` via the `PtyLifecycle` trait (`spawn.rs:213-228`). `PtyHandle::take_reader` gives the reader thread only a `Box<dyn io::Read + Send>` — the reader cannot call `child.wait()` because it has no reference to `child`. So the naive "reader calls child.wait() on EOF" design does not fit the current ownership model. **Second ownership constraint (verified round 2 [TPR-01-1-codex+gemini][high]):** any watcher thread that takes the `child: Box<dyn Child>` also strands `PtyHandle::kill`/`wait`/`try_wait`/`process_id` (used by `oriterm_mux/src/pane/shutdown.rs:17-23` on pane drop) — you cannot take ownership of `child` from `PtyHandle` AND claim `PtyLifecycle::kill` remains "unchanged" without restructuring `PtyHandle` itself. `portable_pty::Child: ChildKiller` (`crates/portable-pty/src/lib.rs:130,150`) exposes `clone_killer() -> Box<dyn ChildKiller + Send + Sync>` (line 157) that returns a separate killer handle which can `kill()` the child independently of who holds the original `Child`. `process_id(&self)` is also a `&self` method that can be captured before moving the child. **Resolution (corrected design):** restructure `PtyHandle` so kill/signal/wait/try_wait all work AFTER the child is moved to the watcher thread. Concretely: (a) `PtyHandle` fields change: replace `child: Box<dyn portable_pty::Child + Send + Sync>` with `killer: Box<dyn portable_pty::ChildKiller + Send + Sync>` (captured at spawn via `child.clone_killer()` before the child itself is moved) + `process_id: Option<u32>` (captured via `child.process_id()` at spawn time) + `exit_result: Arc<Mutex<Option<Result<ExitStatus, String>>>>` (shared with the watcher thread — using `String` for the error half because `io::Error` is NOT `Clone` per round 2 finding [TPR-01-1-codex-r2][high]; the watcher maps `io::Error` → `err.to_string()` before storing, and `PtyLifecycle::wait`/`try_wait` rehydrate via `io::Error::other(s)` so the outside API still returns `io::Result<ExitStatus>`) + `exit_notifier: Arc<Condvar>` (signal used by `PtyHandle::wait()` consumers to block). (b) `PtyHandle::kill(&mut self)` now calls `self.killer.kill()` — no child needed. `PtyHandle::process_id(&self)` returns `self.process_id`. `PtyHandle::wait(&mut self)` acquires the exit_result mutex and `Condvar::wait`s until `Some(_)` is written, then clones the stored `Result<ExitStatus, String>` (both halves are `Clone`) and maps the `String` error half back to `io::Error::other(s)` before returning `io::Result<ExitStatus>` to the caller. `PtyHandle::try_wait(&mut self)` reads the mutex non-blocking (same rehydration on the error half). (c) A dedicated watcher thread spawned at the same time as the child takes ownership of the full `Box<dyn Child>`, calls `child.wait()` blocking, maps the result to `Result<ExitStatus, String>` via `child.wait().map(ExitStatus::from).map_err(|e| e.to_string())`, writes it into `exit_result`, notifies `exit_notifier` (wakes `PtyHandle::wait()` consumers), AND on success sends `ExitStatus` on a new `child_exit_tx: Sender<ExitStatus>` bounded channel (capacity 1 — child exits once). (d) `spawn_pty` in `oriterm_mux/src/pty/spawn.rs:235-264` changes return shape: returns `(PtyHandle, child_exit_rx: Receiver<ExitStatus>)` so the caller can thread the receiver into `PaneIoThread`'s constructor. ONLY `oriterm_mux/src/domain/local.rs:91` (the `spawn_pty(&pty_config)?` call site) consumes the new tuple — `oriterm_mux/src/domain/handoff/mod.rs` does NOT call `spawn_pty` (confirmed round 2 finding [TPR-01-2-codex-r2][medium]: handoff uses `AdoptedPtyHandle` with its own exit-on-EOF semantics via `AdoptedPtyHandle::wait`). The adopted-pane path wires a separate channel: `AdoptedPtyHandle::deliver_exit` (called when the reader observes EOF — see `handoff/mod.rs:68-70`) sends `ExitStatus::synthesized_eof()` (`spawn.rs:56`) on a `child_exit_tx: Sender<ExitStatus>` bounded channel, whose `child_exit_rx` half is threaded into the adopted pane's `IoThreadConfig` at `handoff/mod.rs:141`. This keeps one uniform `PaneIoThread` interface across local + adopted panes without making either path fake an unused channel. (e) `PaneIoThread` gains `child_exit_rx: Receiver<ExitStatus>` as a new field alongside `byte_rx`/`cmd_rx`. Both `select!` blocks in `run()` (lines 141-158 and 161-176) add a `recv(self.child_exit_rx) -> status => { ... }` arm that pushes `Effect::Host(HostEffect::ChildExit { code: status.exit_code() as i32 })`, calls `self.drain_effects_into_mux_events()` to flush, then `return;`s. (f) **Exit-code capture is deterministic, not racy** (round 2 finding [TPR-01-1-gemini-r2][high]): when `byte_rx.recv()` returns `Err(_)` (PTY stream closed — child has exited or is about to), the IO thread enters a "draining" state rather than exiting immediately. It performs: (i) a final `self.drain_effects_into_mux_events()` to flush any in-flight effects from the last parse chunk; (ii) a blocking `self.child_exit_rx.recv_timeout(Duration::from_secs(5))` — 5s is a generous upper bound that accommodates scheduler jitter and signal-delivery delays on loaded systems; empirically `child.wait()` returns within <100ms of EOF on Linux / macOS / Windows when the child has actually exited. (iii) On `Ok(status)`: emit `HostEffect::ChildExit { code: status.exit_code() as i32 }`, drain once more, return. (iv) On `Err(RecvTimeoutError::Timeout)` or `Err(RecvTimeoutError::Disconnected)`: log an error (`log::error!("PaneIoThread: child exit not observed within 5s after EOF; emitting ChildExit {{ code: 0 }} as fallback")`), emit `HostEffect::ChildExit { code: 0 }`, drain once more, return. The 5s upper bound bounds shutdown latency while still being deterministic under normal operation — the previous 50ms was too tight (scheduling jitter on a loaded Windows/Linux system can exceed 50ms routinely). Pin: `pty_eof_exit_code_captured_after_scheduler_delay` — inject a 200ms delay between PTY EOF and watcher `child.wait()` return via a mock; assert `MuxEvent::PaneExited { exit_code: <injected_code> }` (not 0). (g) The existing tests at `oriterm_mux/src/pty/adopt/tests.rs:81-155` (`pty_lifecycle_kill_is_no_op`, `pty_lifecycle_try_wait_returns_*`, `pty_lifecycle_wait_blocks_until_signal_then_unblocks`) MUST still pass — they test `AdoptedPtyHandle`, which is unaffected by this change. `PtyHandle::wait` (separate impl, used by `pane/shutdown.rs:23`) now blocks on `exit_notifier` via the watcher thread instead of blocking inside the child directly, but the observable behavior is identical. (h) No daemon / serialization impact: the watcher + channel are entirely process-local; daemon-mode child-exit is already tracked separately. This restructure is the SSOT-correct way to split ownership: the `Child` trait object has exactly ONE owner (the watcher), the killer has exactly ONE owner (PtyHandle via the cloned killer), process_id is captured at spawn (not re-queried), and wait/try_wait consumers block on a canonical exit-status cell. Pinned by semantic test `pty_eof_emits_pane_exited_via_effect_router` in `effect_router/tests.rs` — construct `PaneIoThread<QueueingEffectSink>` with a mock `byte_rx` that sends `Ok(b"x".to_vec())` then drops its sender, and a mock `child_exit_rx` that forwards `ExitStatus { code: 42, signal: None }` before dropping; assert `mux_rx.recv_timeout(5s)` returns `MuxEvent::PaneExited { pane_id, exit_code: 42 }`. 12. **`ResponseToken<T>::fulfill()` is last-write-wins — duplicate fulfillment silently overwrites** (new, from Phase 4 architectural-risk §1). `oriterm_core/src/effect/families/host_request.rs:69-71` does `*self.slot.lock() = Some(value)` unconditionally — a second `fulfill()` call silently replaces the first value; the first `take()` sees whichever write landed last. Because `ResponseToken<T>: Clone` (`host_request.rs:53`), a token can be cloned into BOTH `register_host_request_response` (IO-thread pending poll) AND `MuxEvent::HostClipboardLoad::reply` (main-thread fulfill path) — if a future consumer accidentally fulfills from two sites (e.g. an overlay widget AND the main clipboard handler race), the duplicate fulfill is undetectable. **Resolution:** 01.2 adds single-assignment semantics to `ResponseToken<T>::fulfill` — the method becomes `pub fn fulfill(&self, value: T) -> Result<(), AlreadyFulfilled>` returning `Err` if the slot is already `Some(_)`. Callers (`PaneIoHandle::fulfill_clipboard_load`, `PaneIoHandle::fulfill_color_query`) `.expect("ResponseToken fulfilled twice — duplicate MuxEvent::HostClipboardLoad routing")` because a double-fulfill is a routing bug. Negative pin `response_token_rejects_double_fulfillment` in `oriterm_core/src/effect/families/host_request/tests.rs` (requires converting `host_request.rs` → `host_request/mod.rs` + `host_request/tests.rs` per `.claude/rules/test-organization.md` §Sibling tests.rs Pattern; the conversion is PART of 01.2's implementation, not deferred). This is an intentional API-shape change in `oriterm_core` — the impacted sites are the legacy adapter at `legacy/mod.rs` (deleted in 01.3 — no update needed) and the new `register_host_request_response` / fulfill helpers (in scope for 01.2).
13. **`PendingResponse` leaks forever if consumer drops its handle unfulfilled** (new, from Phase 4 blind-spot §4; unified round-4 [TPR-01-3-codex-r4][medium] — single cancellation design). `oriterm_mux/src/pane/io_thread/response_poll.rs:48-55, 64-71` moves the `ResponseToken<T>` into a `Box<dyn FnMut() -> Option<Effect>>` closure captured inside `PendingResponse`. The closure holds an `Arc<Mutex<Option<T>>>` via the token. If the main-thread consumer (e.g. the clipboard handler) drops its `MuxEvent::HostClipboardLoad::reply` handle WITHOUT calling `fulfill_clipboard_load` (user dismisses a permission prompt, overlay closes, pane closes mid-request), the IO thread's `pending_responses` entry keeps the token's `Arc` alive forever — `poll_pending_responses()` polls it every tick and `reply.take()` always returns `None`. The `pending_responses: Vec<PendingResponse>` grows unboundedly under this pattern (violates RSS invariant, violates the wake-channel collapse semantic). **Resolution (unified Arc-only design — no Weak):** 01.2 adds cancellation detection via `Arc::strong_count`. `PendingResponse` stores a clone of the token's `slot: Arc<Mutex<Option<T>>>` (captured at registration); the main-thread-facing `ResponseToken<T>` holds another `Arc` clone. When both are live, `Arc::strong_count(&self.slot) == 2` (one pending + one consumer). When the consumer drops the handle, `Arc::strong_count(&self.slot) == 1` (only the IO-thread pending holds it). `PendingResponse::poll` checks `Arc::strong_count(&self.slot) <= 1` AFTER calling `take()` returns `None` — if the consumer side is gone AND the slot is still empty, the entry is cancelled (returns `PollResult::Cancelled`) and `poll_pending_responses()` removes it from the vector WITHOUT pushing a PTY write. No `Weak` reference is used — the pending's own Arc is what keeps the slot alive across the `take()` call, and strong_count discriminates consumer-dropped from still-live based on whether the MAIN-thread Arc exists. Pinned by `pending_response_cancelled_when_consumer_handle_dropped` in `response_poll/tests.rs` — register a host request, drop the main-thread `reply` handle, run `poll_pending_responses()` twice, assert `t.pending_responses.is_empty()` AFTER the second call (the two-tick delay handles the race where the consumer hasn't dropped yet at the moment of registration) and NO `MuxEvent::PtyWrite` was emitted. Bounded by `debug_assert!(self.pending_responses.len() < MAX_PENDING_RESPONSES = 64)` so even a detection bug surfaces before production runs blow RSS. This design lives in `oriterm_core` alongside `PendingResponse`/`ResponseToken`/`PollResult` — the `oriterm_mux`-side `poll_pending_responses` consumes the `PollResult` variants but does not own the cancellation logic (SSOT: detection policy is in `oriterm_core`).
14. **One wake must drain ALL ready tokens** (new, from Phase 4 blind-spot §5). The wake channel is `crossbeam_channel::bounded(1)` with `try_send()` coalescing — two fulfills between wakes collapse to one wake. The IO thread's `select!` unblocks once; the next iteration calls `drain_commands → poll_pending_responses` which DOES iterate every `pending_responses` entry (`response_poll.rs:90-100` — correct). But the `handle_bytes` path's drain is NOT in the no-byte-activity idle path — only `drain_commands` runs between wakes (sync-deadline + command arm). **Resolution:** 01.2 pins that `poll_pending_responses` drains EVERY ready token on a single wake — `two_fulfills_one_wake_drain_both_tokens` in `response_poll/tests.rs`: register two tokens, fulfill both, send ONE wake signal, run ONE loop iteration, assert BOTH produce `MuxEvent::PtyWrite` via the `drain_effects_into_mux_events()` call at the end of `drain_commands`. This proves the wake-collapse contract is safe: one wake, N drains, N replies.
15. **`PtyEffect::Write { bytes: Vec<u8> }` → `MuxEvent::PtyWrite { data: String }` is a lossy boundary** (new, from Phase 4 architectural-risk §2). Confirmed: `oriterm_core/src/effect/families/pty.rs` has `PtyEffect::Write { bytes: Vec<u8>, kind: PtyWriteKind }`; `oriterm_mux/src/mux_event/mod.rs:67-73` defines `MuxEvent::PtyWrite { pane_id: PaneId, data: String }`; the legacy adapter at `legacy/mod.rs:101-103` converts via `String::from_utf8_lossy(&bytes).into_owned()`. Non-UTF-8 replies (binary Kitty Graphics replies, raw DA2 with 0x9C, future binary protocols) get corrupted at this boundary — invalid UTF-8 bytes become `U+FFFD` before reaching the PTY write. Today's OSC 52 / OSC 10-12 replies are ASCII so this is latent, but the EFFECT variant is correctly `Vec<u8>` and silently downgrading to `String` at the mux boundary is an SSOT violation — the byte-exact reply is authoritative. **Resolution:** 01.1 changes `MuxEvent::PtyWrite::data` from `String` to `Vec<u8>` (SAME commit as the new variants). Compiler drives every downstream consumer — `oriterm_mux/src/in_process/event_pump.rs`, `oriterm/src/app/mux_pump/mod.rs`, `oriterm_mux/src/server/notify/mod.rs`, `oriterm_mux/src/backend/client/notification.rs`, `oriterm_mux/src/protocol/messages.rs` (`NotifyPtyWrite` PDU if it exists must also be `Vec<u8>`). Update `fmt::Debug for MuxEvent` at `mux_event/mod.rs:114-115` to `write!(f, "PtyWrite({pane_id}, {} bytes)", data.len())` (unchanged format). Pinned by `pty_write_preserves_non_utf8_bytes` in `effect_router/tests.rs` — push `PtyEffect::Write { bytes: vec![0x90, 0xFF, 0x00, 0x80] }`, drain, assert `mux_rx.recv()` yields `MuxEvent::PtyWrite { data: vec![0x90, 0xFF, 0x00, 0x80] }` byte-exact (not `String::from_utf8_lossy`'d). **This change has blast radius — it's why 01.1's cross-crate commit is large, not a reason to skip it.**

## Architectural Context (read before implementing)

Current state (verified against code at the time of this review):

- IO thread's `Term<S>` type parameter is `S: EffectSink + 'static`. Today `S = LegacyEventSink<IoThreadEventProxy>`. Construction sites: `oriterm_mux/src/domain/local.rs:139-145` and `oriterm_mux/src/domain/handoff/mod.rs:116-122` both call `Term::new(.., LegacyEventSink::new(IoThreadEventProxy::new(..)))`.
