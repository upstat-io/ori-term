## §1 — Core Design Philosophy (KEEP THIS)

1. **Main-context orchestrator.** `/tpr-review`'s round loop runs in the caller's main conversation. No `context: fork`. Every tool call, every finding, every edit is visible to the user in real time. The old system hid this behind envelope/polling/triage-sub-agent; the rewrite's whole point was visibility.

2. **Parallel Agent dispatch per reviewer.** Each round: ONE assistant message with TWO `Agent({subagent_type: "general-purpose", model: "sonnet", prompt: <filled tp_agent_prompt.md>})` calls. They run concurrently per https://code.claude.com/docs/en/sub-agents. Wall-clock = `max(codex, gemini)`. No per-tool completion callbacks (undocumented); treat results as batch-complete.

3. **Plain-text transport.** Reviewers emit a fenced `<<<TPR-REPORT … TPR-REPORT>>>` block at the end of their CLI output. The orchestrator parses it inline. No JSON envelope, no schema, no merger script, no polling, no background process.

4. **Grounding by reference, not by embedding.** The inner prompt passed to codex/gemini tells the CLI to `ls .claude/rules/*.md` and `cat` each one itself. Do NOT embed `CLAUDE.md` + 28 rule files into the prompt argv — that's ~700KB and blows past Linux `ARG_MAX` (~128KB) with `Argument list too long`.

5. **Verification-against-code discipline.** Every reviewer finding is a **hypothesis**, not a fact. The orchestrator (main context) reads the cited file, confirms the quote exists verbatim, and drops unverifiable findings before classification. Trust tier sets verification **depth**, not pass/fail:
   - Codex HIGH → spot-check (read ±20 lines of cited range)
   - Gemini LOWER → full-verify (read cited file in full, trace behavior end-to-end)

6. **One main-context edit path.** When actionable findings land, the orchestrator edits code directly. No hand-off to a fix sub-agent, no separate edit phase. Feedback loop stays tight and visible.

7. **No `@`-includes in the new skill files.** `@`-includes are undocumented per the Claude Code skills reference. The rewrite deliberately avoided them. Exception: `compose-intel-summary.md` is still `@`-included by 20 OTHER consumers — that's legitimate pre-existing usage outside the rewrite's scope.

8. **Per-invocation unique scratch dirs.** Use `mktemp -d -t <prefix>-XXXXXXXX` in reviewer sub-agents. Hard-coded `/tmp/...` subdirs COLLIDE across parallel Claude sessions (the user routinely runs concurrent sessions). This is load-bearing — see §Regressions To Watch For.

9. **CLAUDE.md-compliant timeouts.** `timeout: 2700000` (45 min) on the foreground Bash call to the reviewer CLI. The `.claude/hooks/block-banned-commands.sh` hook blocks any `timeout` under `1200000` ms on codex/gemini commands. Never set `600000` or lower.

10. **Always-on spec/grammar gate.** `/tpr-review` §3 runs in ALL modes (work / plan / custom-objective). The rule it enforces — `.claude/rules/spec.md §Enforcement` — has no mode exemption. The gate is cheap (one git diff + one ls) and gating it by mode creates a coverage hole that custom-objective reviews can drive through.

## §4 — Lessons from the Dogfood Runs (2026-04-16)

### 2026-04-18 — Liveness probe closes the kill-deep-agents bias

**Finding source:** User `/improve-tooling` invocation: "in the old /tpr-review workflow there was a system to check and see if an agent was still busy or not by monitoring several factors. it worked well, currently you tend to kill agents if they are deep in thought but not emitting output thinking they are dead which means we are favoring shallow agent work but killing them when they do deep investigation. thoughts on fix?"

**Symptom:** Since the 2026-04-16 rewrite, the orchestrator has been treating reviewer silence as a binary signal — present (alive) or absent (dead). Silence ≥ 5 min biased the retry/abort decision toward abort, especially after the both-reviewer-failure path triggered. In practice, codex and gemini reviewers frequently dispatch a slow `Bash` tool call (`cargo build`, `cargo test --all`, `grep` over a large corpus) that legitimately takes 5-10 minutes, during which nothing appears on the tee'd stdout. Under the pre-probe logic, those reviewers looked identical to hung CLIs — the agents doing the deepest investigation were exactly the ones most likely to get killed and retried.

**Root cause:** The 2026-04-16 rewrite deleted the `.claude/skills/dual-tpr/` infrastructure wholesale, including its `scripts/status-check.sh` multi-factor liveness probe. The rewrite correctly identified that the old envelope/polling architecture was over-engineered, but the probe itself was doing necessary work — distinguishing "waiting on slow tool" from "genuinely hung." Without it, the main-context orchestrator has no evidence to consult before retrying, and guesses conservatively (favoring retry).

A secondary factor: the I14 dual-path-transport fix (2026-04-16 evening) made reviewer stdout land on disk live via `tee`, but no consumer was reading the tee output before retry decisions. The groundwork was there; the consumer was missing.

**Fix:**

1. **`diagnostics/tpr-liveness.sh`** (new, ~180 lines). Reads `$scratch/{reviewer}-stdout.txt`, classifies as `alive` / `quiet` / `dead` using three factors: (a) mtime-age against a tunable `--grace-seconds` (default 300), (b) byte-growth presence, (c) trailing-line content pattern (tool_call / thinking / final_report_marker / stream_event). A fresh `tool_call` signal extends the dead threshold to 4·grace (default 20 min) — explicitly to cover slow Bash invocations inside a reviewer. Exit codes encode the verdict for shell orchestration. `--json` for machine parsing, `--human` for transcript-readable output, `--help` with the full three-state decision table.
2. **`.claude/skills/tpr-review/SKILL.md` §9** — added "Liveness probe" step BEFORE "Stranded-report recovery" and BEFORE the both-reviewer-failure retry dispatch. The probe gates every retry decision: `alive` → wait, do not retry; `quiet` → probe once more before retrying; `dead` → fall through to stranded-report recovery, then retry if that also yields nothing. Both the one-reviewer-failed and both-reviewers-failed paths now consult the probe first.
3. **Invariant I19 added** (this file, §2): probe verdict MUST gate retry/abort before a reviewer can be declared failed. Supported by a §5 regression line for future edits that might regress the §9 path.
4. **Doc sync:** `diagnostics/README.md` (canonical) grew a full usage section + three-state decision table + entry in the quick-reference table. `.claude/rules/diagnostic.md` (secondary surface) grew a row in the scripts table.
5. **Stale MEMORY.md pointer fixed:** the user's `feedback_dual_tpr_polling.md` memory still referenced `.claude/skills/dual-tpr/scripts/status-check.sh` — deleted in the 2026-04-16 rewrite. Rewritten to reflect the current architecture and point at the new probe.

**Insight:** The probe intentionally does NOT re-create the old polling protocol — there's no 5-min loop, no `$RUN/launch.time` anchor, no per-poll commentary. In the parallel-Agent-dispatch architecture, the main context BLOCKS on the Agents until they return; polling during a blocked wait is architecturally impossible. The probe is therefore a **post-return retry-decision input**, not a heartbeat renderer. That's still a big upgrade from the binary signal — the three-state verdict tells the orchestrator *why* silence happened, not just that it did. The remaining mid-stream visibility work (the rendering half of the old [p2] item) is now scope for a future `improve-tooling` session: with the probe as a backend primitive, a heartbeat render pass becomes straightforward.

**Bounded risk:** a probe that's too permissive lets a truly hung CLI burn the full 45-min `block-banned-commands.sh` ceiling. Erring permissive is the correct trade here — the worst case (45 min lost to a hang) is bounded by the hook; the worst case for false-negatives (killing a deep-investigating agent) is unbounded in the wrong direction: shallow reviewer work compounds into shallow findings, which compound into missed bugs shipping.

### 2026-04-17 (help-mode refactor) — `/tp-help` collapsed to thin delegator over `/tpr-review --help-mode`

**Finding source:** User `/improve-tooling` invocation: "make sure /tp-help is using /tpr-review with rounds 1, and custom prompting instead of having it's own internal way of calling tp agents."

**Symptom:** Pre-refactor, `/tp-help` duplicated the dispatch machinery that `/tpr-review` already owned — its own `tp_help_prompt.md` sub-agent template (150 lines), its own `mktemp -d` scratch-dir creation, its own parallel `Agent()` dispatch with `subagent_type: "general-purpose"`, its own codex `--full-auto --json --ephemeral` / gemini `-m gemini-3.1-pro-preview --approval-mode yolo --output-format stream-json` invocation strings, its own `timeout: 2700000`, its own `<<<TPHELP-RESPONSE>>>` sentinel extraction, its own failure retry ladder. Every invariant from `/tpr-review`'s 2026-04-16 rewrite (I1–I16) had to be manually kept in sync across two sub-agent templates. When `/tpr-review`'s `tp_agent_prompt.md` Step 2 added `| tee "$RUN/{REVIEWER}-stdout.txt"` (I14, to fix the stranded-report failure mode in the 2026-04-16 evening dogfood), `tp_help_prompt.md` did NOT receive the same fix — it still lacked the `tee` as of this refactor. The duplication was not merely redundant; it was a live drift vector.

**Root cause:** Two skills with overlapping dispatch semantics and diverging maintenance paths. `/tpr-review` is about finding bugs (verify-against-code → classify → fix-and-commit → file); `/tp-help` is about providing advice (raw prose, no filing, no edits). But the **transport layer** underneath both was identical: one scratch dir, two parallel CLI invocations, sentinel-extracted responses. Pre-refactor, the transport layer lived in TWO files (`tp_agent_prompt.md` for review, `tp_help_prompt.md` for help) with zero deduplication. The correct shape collapses the transport to one surface (`/tpr-review`'s dispatch) and distinguishes modes in the orchestrator (finding body vs. advice body).

**Fix:** Three files touched + one file deleted.

1. `tpr-review/SKILL.md` §1 — added `--help-mode` composable flag. When set: forces `max_rounds = 1`, switches §5 to a dedicated help-mode branch that (a) skips §4 verify-against-code (advice is prose, no file:line to verify), (b) skips §6 meta classification (advice is not a finding), (c) skips §7 fix-and-commit (help mode never edits code), (d) skips §10 plan-TPR integration (advice is not filed), (e) skips the §5 cap-exit `AskUserQuestion` (help mode has no convergence loop — it is one-shot by contract), (f) KEEPS §2 grounding + §3 spec-gate (spec governance has no mode exemption; advice must still be grounded in project conventions). The help-mode branch composes the help-mode body via `compose-round-prompt.md`, dispatches both reviewers through the same thin-transport sub-agent pattern `tp_agent_prompt.md` already implements, extracts `response:` prose from each TPR-REPORT envelope, and emits the `<!-- TP-HELP BEGIN/END -->`-attributed concatenated block at §11.H.

2. `tpr-review/compose-round-prompt.md` — added help-mode shared body. Return schema uses `mode: help` + `status: advice | failed` + `response: |` prose (discriminator lets the coordinator branch on `mode:` when parsing). Grounding block unchanged (reviewers still `ls .claude/rules/*.md` and read the manifest). Banned-hedges list tailored for advice ("it depends", "for safety", etc.) rather than review hedges ("pre-existing", "out of scope"). No Prior-Round State block and no Thoroughness Directive — help mode is stateless and one-shot.

3. `tp-help/SKILL.md` — rewritten as a thin delegator (~170 lines, down from 310 lines across SKILL.md + tp_help_prompt.md). Owns only: auto-trigger detection (§2), context assembly into a composed objective (§3), delegation via `Skill({skill: "tpr-review", args: "--help-mode --max-rounds=1 " + composed_objective})` (§4), output pass-through (§5), and caller-side interpretation guidance (§6). Has zero direct `Agent()` calls, zero scratch-dir management, zero CLI invocation. All dispatch complexity lives in `/tpr-review`.

4. `tp-help/tp_help_prompt.md` — **deleted**. The sub-agent prompt template is replaced by `compose-round-prompt.md`'s help-mode body, which is reached through the canonical `/tpr-review` transport. No other consumers of `tp_help_prompt.md` existed.

**Why the discriminator is inside the TPR-REPORT envelope, not a distinct sentinel:** An earlier draft considered introducing `<<<TPHELP-RESPONSE>>>` sentinels for help mode. Rejected: that would require parameterizing `tp_agent_prompt.md` Step 3's `sed` extractor (`sed -n '/<<<TPR-REPORT/,/TPR-REPORT>>>/p'`) with a variable sentinel name, adding a transport-layer distinction that doesn't add value. The transport is content-agnostic; the discriminator belongs inside the content. `mode: help` + `response: |` vs. `status: clean | findings | failed` + `findings: [...]` is a schema-variant, not a transport-variant — the coordinator parses the shared envelope and branches on `mode:` when present. `tp_agent_prompt.md` stays identity-neutral and mode-neutral.

**Why spec-gate still runs in help mode:** Spec governance is a universal invariant per `spec.md §Enforcement`. A user asking "how should I change this lexer token" triggers the same spec-gate as "review my lexer changes" — if the working tree has uncommitted spec/grammar diff without an approved proposal, both flows must surface the violation before running reviewers. Exempting help mode would create a bypass channel ("ask for advice on this spec change, get zero governance friction"). Autonomous-mode handling is unchanged (exit with `autonomous_spec_gate_violation`).

**Callers unchanged:** `/fix-bug` Phase 1.75, `/create-plan` Step 6B/8B, `/review-plan` Step 4, and proactive auto-triggers all invoke `/tp-help` as a slash-command reference in prose. The slash-command contract (name, ARGS, `<!-- TP-HELP BEGIN/END -->` concatenated-block output) is preserved byte-for-byte. Callers do NOT need to know about the `/tpr-review --help-mode` delegation — that's an implementation detail below the slash-command surface.

**Invariants added to §2:**
- I17 (new): `/tp-help` is a thin delegator over `/tpr-review --help-mode --max-rounds=1`. It owns auto-trigger, context assembly, and caller-side interpretation ONLY. It does NOT dispatch sub-agents, manage scratch dirs, invoke reviewer CLIs, or parse raw CLI output. All dispatch complexity lives in `/tpr-review`.
- I18 (new): Help mode uses the same `<<<TPR-REPORT>>>` sentinels as review mode; the discriminator is `mode: help` inside the envelope + `response: |` prose instead of `findings: [...]`. Introducing a distinct `<<<TPHELP-RESPONSE>>>` sentinel is a regression — it forces the transport layer to care about mode.

**Regressions to watch:** any Agent() calls in `tp-help/SKILL.md`, any `codex exec`/`gemini -m` invocations in `tp-help/SKILL.md`, any re-appearance of `tp_help_prompt.md` (or a file playing its role), any `<<<TPHELP-RESPONSE>>>` sentinel usage in new code, any `/tp-help` invocation NOT delegating via `Skill({skill: "tpr-review", args: "--help-mode ..."})`.

### 2026-04-17 — Prompt-composition moved from sub-agents to orchestrator (Opus)

**Finding source:** Live user feedback during a `/tpr-review` invocation on `/review-plan` review. User observed: "Sonnet is writing the prompt and doing a terrible job. In the previous version (pre-`f386c7cd`) that was overcomplicated overall but did one thing well: it wrote a new prompt each round based on findings from prior rounds to push toward consensus. Have Opus write the prompt at the beginning of the round and hand it to each agent — and Sonnet's entire mission must be to parse and copy-paste findings, not translate in any way."

**Symptom:** In the simplified version, `tp_agent_prompt.md` had each Sonnet sub-agent compose its own inner reviewer prompt via a heredoc in Step 1. That meant:
1. Prompt composition ran TWICE per round (codex + gemini), identically, by two separate Sonnet instances.
2. The composition had zero awareness of prior-round findings — every round sent the same generic prompt, so no convergence pressure.
3. Sonnet sub-agents drifted into editorial work: paraphrasing findings, "improving" titles, dropping findings they thought were wrong.

**Root cause:** The 2026-04-15 simplification correctly collapsed the setup/triage/final-report sub-agent triad into a main-context loop, but accidentally left prompt composition inside the per-reviewer sub-agent template — the one place it had always been wrong. Editorial judgment belongs to Opus; Sonnet sub-agents should be pure transport.

### 2026-04-17 (evening) — Autonomous-mode flag added

**Finding source:** User feedback during the same dogfood session, after Round 1 commit: "/tpr-review is used inside of autonomous skills like /sync-docs and in those cases instead of userprompt when you would normally userprompt you would just use best judgement to either continue or finish that loop."

**Gap:** `/sync-docs` runs on a cron schedule (its description: "Nightly-ready, fully automated, fact-bound"). If it called `/tpr-review` and `/tpr-review` hit a cap-exit, both-reviewer-failure, context-pressure-pause, or spec-gate `AskUserQuestion`, the batch would hang forever — there's no user at the keyboard. The pre-autonomous skill had no way to recognize "I'm being called without a human" and substitute best-judgement auto-decisions.

**Fix:** Added an `autonomous_mode` flag to `/tpr-review`, detected via `--autonomous` in `ARGS`. When set, every `AskUserQuestion` listed in §11.5 items 1-5 is replaced by a best-judgement auto-decision that emits a distinct `exit_reason`:

| Choice point | Interactive | Autonomous auto-decision | `exit_reason` |
|---|---|---|---|
| §5 cap-exit, all_meta | accept-with-findings | auto-accept | `autonomous_accept_at_*` |
| §5 cap-exit, substantive | user picks 4 options | auto-exit | `autonomous_exit_substantive_at_*` |
| §9 both-reviewer-failure-twice | AskUserQuestion 3 options | auto-exit | `autonomous_transport_failure` |
| §9 context-pressure pause | optional AskUserQuestion | never inserted | n/a |
| §3 spec-gate violation | finding filed, user fixes | auto-exit | `autonomous_spec_gate_violation` |

Key design choices:

1. **Never silently auto-accept substantive findings.** Autonomous mode maps substantive-findings cap-exit to `autonomous_exit_substantive_at_*`, not `autonomous_accept`. The review still runs, findings still file, but `reviewed: false` stays — the parent batch aggregates these in its end-of-run report. Auto-accepting would mask real issues across a nightly run.
2. **Never auto-extend the iteration cap.** `run-more` requires a user; autonomous stays cap-bounded. Extending without a human means running forever on a real transport bug.
3. **Never auto-retry on spec-gate violation.** Spec/grammar changes without governance are correctness-sensitive in a way autonomous mode cannot sign off on. Exit + alarm the parent.
4. **§10 plan-mode integration landed the flip for `autonomous_accept_at_*`** (same semantics as `user_accepted_at_*`) — both lead to `reviewed: true` with a notes-line recording decision provenance. The `autonomous_exit_substantive`, `autonomous_transport_failure`, and `autonomous_spec_gate_violation` cases leave `reviewed: false` and set `third_party_review.status: escalated`.

**Adoption.** Consumers like `/sync-docs` that invoke `/tpr-review` unattended MUST pass `--autonomous`. Interactive callers (`/review-plan`, `/fix-bug`, direct user invocation) MUST NOT — best-judgement auto-decisions are strictly worse than human answers when a human is available.

**Invariant (add to §2 future edit):** "`/tpr-review` has two invocation modes: interactive (default) and autonomous (`--autonomous` flag). Autonomous mode replaces every coordinator-level `AskUserQuestion` with a best-judgement auto-decision whose `exit_reason` is distinct so the parent batch can triage outcomes. Silently mapping autonomous statuses to 'clean' in the parent defeats the policy."

### Cross-round patterns (generalizable)

- **Architectural fixes land cleanly; doc drift lingers.** Round 0 fixed architecture (gemini clean). Round 1 caught the *next* architectural issues (gemini agreed on timeout/spec-gate). Round 2 found only doc-text drift (gemini clean again). The sequence of findings tracks the code's actual maturation.
- **Gemini LOWER-trust is worth it.** Gemini was clean 2/3 rounds, which is a strong convergence signal rather than a weakness. When both reviewers agree on a finding, it's almost certainly a real architectural issue. When only codex flags, it's usually doc consistency.
- **Trust-tier aware verification is load-bearing.** Codex cited accurate line numbers in 100% of findings across 3 rounds. Gemini's citations (when it had any) also matched — but the LOWER-trust discipline of "re-read file in full" caught drift in the round-1 timeout issue that codex's spot-check alone would have missed on a different codebase.
- **Doc-string drift is the long tail.** After the architectural fixes, the remaining findings (rounds 2) were all doc text that referenced the OLD behavior (10-min timeout, old `/tmp` path). When fixing an architectural invariant, grep the ENTIRE file for references to the old value and update them all at once.

## §7 — How To Use This File In Future Sessions

**On every surprise.** When you run `/tpr-review` or `/tp-help` and something unexpected happens (failure mode, bad output, confusion about what the skill is doing), come here first. Check §Regressions To Watch For — is the surprise a known regression pattern? Check §Improvement Log — is it already filed? If neither, add it.

**Before editing any of the 6 canonical files in §3.** Re-read §Load-Bearing Invariants. Every invariant there is defended by a specific failure mode from the dogfood runs. Breaking an invariant without understanding its failure mode means re-running the dogfood to re-discover what this file already records.

**When `/fix-bug` or `/tpr-review` on a real bug fails.** If the failure is in the *skill* (not the bug being fixed), log it here with the specific invocation that triggered it. This is the correct home for skill-level bugs — it's a file dedicated to this skill pair, inside the improve-tooling skill folder (which itself is the canonical home for "improve the tooling, don't work around it" per `CLAUDE.md §Continuous improvement everywhere`).

**When the design evolves.** If you change §1 Core Design Philosophy or §2 Load-Bearing Invariants, update both SKILL.md files to match AND add a dated entry under §4 Lessons documenting why the invariant changed. Don't silently mutate the design — the whole point of this file is that the design doesn't get lost.
