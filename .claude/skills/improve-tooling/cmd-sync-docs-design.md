# `/sync-docs` — Design Notes and Improvement Log

## §Purpose + Context

`/sync-docs` is the project's comprehensive nightly documentation sync command at `.claude/commands/sync-docs.md`.

- Runs unattended overnight; iterates through 14 batches of related doc files.
- Each batch launches `/tpr-review --autonomous` with a custom objective; Codex + Gemini cross-check every claim against code/spec/missions/plans; Claude fixes findings and loops until both reviewers report clean.
- Contracts: two-tier Fact-Pairing (Tier A intent + Tier B corroboration); factual-only edit-scope taxonomy (§"The One-and-a-Half Rule"); `scripts/prose-lint.py` pre-commit gate; Fact-Pairing exception categories (`TRIVIAL`, `INTENT-ORPHAN/operational`, `INTENT-ORPHAN/deletion`).

**Last significant change (2026-04-19):** `/improve-tooling` invocation that (a) unbanned `plans/**` from Banned Paths (kept `plans/completed/**` + `plans/bug-tracker/**` banned), (b) added new Batch 13 "Roadmap + Active Plans (FACTUAL ALIGNMENT ONLY)" with a narrow allowed-edits table + banned-edits list scoped to preserve plan lifecycle content (status/checkboxes/HISTORY/descriptions), (c) renumbered the catch-all to Batch 14, (d) added "The One-and-a-Half Rule: SCOPE OF ALLOWED EDITS (Factual-Only, Zero Prose)" — a taxonomy of allowed vs banned edit categories that closes the prose-creep gap Fact-Pairing alone does not catch, (e) wired `scripts/prose-lint.py` as a MANDATORY pre-commit gate in Batch Execution Protocol step 5 (exit 1 blocks commit; bypass banned), (f) prepended the SCOPE-OF-ALLOWED-EDITS block to every batch's `/tpr-review --autonomous` ARGS alongside GRAPH-FIRST PROTOCOL. User feedback driving the change: "The single most important part of this command by far, beyond everything else is grounded factual changes. I still feel it's doing some prose updates to things that it should definitely not be doing. All changes need to be prescriptive only."

**Previous significant change (2026-04-18):** `/improve-tooling` invocation that (a) wired `/sync-docs` as the 21st consumer of the intelligence-graph SSOT (`compose-intel-summary.md`), (b) added Phase 0.6 "Intelligence Pre-Sweep" materializing `file-symbols`/preset/`plan-status`/`similar` output to `/tmp/sync-docs-intel/` before batch 1, (c) added a shared "Graph-First Verification" instruction block prepended to every batch's `/tpr-review --autonomous` ARGS so reviewer sub-agents use the graph too, and (d) fixed a critical autonomous-flag bug where `/sync-docs` was invoking `/tpr-review` in interactive mode — any cap-exit / ambiguous-input / transport-failure branch would hit `AskUserQuestion` and hang the nightly run waiting for a user who is asleep.

**Approved plan:** none — `/improve-tooling` changes go through direct commit per CLAUDE.md §Scope (skills/tooling/infra exempt from `/tpr-review` gating because `/fix-bug` + `/tpr-review` would be circular).

## §1 Core Design Philosophy (KEEP THIS)

1. **Nightly-unattended contract.** The command runs for HOURS with ZERO human interaction. Every subsystem it invokes (currently only `/tpr-review`, but future integrations too) MUST have an autonomous/non-interactive mode, and `/sync-docs` MUST invoke them with that mode engaged. An interactive sub-command is a contract violation — the entire nightly sync hangs the first time a branch falls back to `AskUserQuestion`. Enforce via explicit flag-presence in §Batch Execution Protocol step 2 + §Automation Protocol step 3.

2. **Worktree isolation (Phase 0).** All work happens on a branch inside `.claude/worktrees/sync-docs-YYYY-MM-DD`. Never modify the `dev` branch in place. User reviews and merges when ready.

3. **Discovery is rule-based, not enumerated.** Phase 0.5 uses `git ls-files '*.md'` filtered by the Banned Paths list. New `.md` files land in Batch 13 (the catch-all) automatically — there is no maintenance obligation when a new doc surface appears.

4. **13 sequential batches, never parallel.** Earlier batches establish Tier-A intent surfaces (canon, missions, rules) that later batches verify against. Running them in parallel would break the intent-propagation ordering.

5. **Per-batch sequential launch of `/tpr-review --autonomous`.** The TPR skill handles reviewer launch, fix-and-rerun loops, autonomous exit semantics. `/sync-docs` is a dispatcher — it does NOT re-implement TPR transport or reviewer orchestration.

6. **Two-tier Fact-Pairing contract.** Every Edit carries a `Fact-Pairing:` block with ONE Tier A (intent) citation + ONE Tier B (corroboration) citation. Tier A sources are ranked: spec clause → approved proposal → mission → design-philosophy header. Tier B is implementation fact, cross-doc coherence, or graph-verified fact with source spot-check. `TRIVIAL`, `INTENT-ORPHAN/operational` (enumerated surfaces only), and `INTENT-ORPHAN/deletion` are the exceptions, explicitly tagged.

7. **Intent NEVER edited to match code.** When intent and code disagree, the bug is filed against the CODE side — never against the intent surface (missions, spec, proposals). This is the load-bearing drift-surfacing invariant.

8. **Graph-first discipline (2026-04-18).** Every reviewer sub-agent uses the intelligence graph BEFORE manual grep. Phase 0.6 materializes the baseline inventory once; per-batch objectives cite the shared Graph-First Protocol block (§Batch Definitions) so reviewers extend with on-demand queries. Graph results are DISCOVERY; source verification is still load-bearing.

9. **Graceful degradation when graph unavailable.** `scripts/intel-query.sh status` probe; if down, Phase 0.6 is skipped and every batch's findings are prefixed `graph-unavailable:` in the Phase 3 report. Never fail the sync over an unavailable graph.

10. **Commit per batch, no push from worktree.** Each batch's changes are committed via `/commit-push` to the worktree branch. User merges at their discretion. Never push from the worktree.

11. **Grounded factual corrections only — zero prose (2026-04-19).** Every Edit falls into the allowed-categories table in §"The One-and-a-Half Rule" (wrong file path / wrong symbol / wrong crate / stale rule anchor / wrong spec clause / wrong env var / broken cross-ref / wrong count / wrong signature fragment / INTENT-ORPHAN deletion / TRIVIAL). Every Edit OUTSIDE that table is a CRITICAL TPR finding — even with valid Tier A + Tier B citations. Fact-Pairing catches UN-grounded edits; this rule catches GROUNDED-PROSE edits. Enforced by `scripts/prose-lint.py` at Batch Execution Protocol step 5 and by explicit reviewer instruction in every batch's prepended SCOPE-OF-ALLOWED-EDITS block.

12. **Plans + Roadmap in scope (2026-04-19), lifecycle content banned.** `plans/**` is no longer a banned path (except `plans/completed/**` + `plans/bug-tracker/**`). New Batch 13 verifies factual claims in active plans + roadmap against rules/missions/spec/code. Lifecycle content (`status:`, checkbox state, `review_pipeline:`, `HISTORY`, subsection status markers, task descriptions, success criteria) is banned from edits — drift touching lifecycle content surfaces via `/add-bug` subsystem `docs`, never via plan rewrite.

## §2 Load-Bearing Invariants

Changing any of these without a concrete plan risks re-introducing the failure modes listed:

| # | Invariant | Why (which failure mode it prevents) |
|---|-----------|--------------------------------------|
| I1 | Every `/tpr-review` launch from `/sync-docs` MUST include `--autonomous` as the first flag | Without it, any `/tpr-review §5 §9 §1` terminal branch (cap-exit / transport-failure / ambiguous-input) falls back to `AskUserQuestion` and hangs the nightly sync indefinitely. The user launches this command and sleeps; a hung prompt breaks the entire contract. |
| I2 | 13 batches run SEQUENTIALLY, not in parallel | Earlier batches (canon.md, missions.md) establish Tier-A intent that later batches verify against. Parallel execution would inject cycles into the intent-propagation DAG. |
| I3 | Phase 0.6 pre-sweep runs ONCE per nightly run, materialized to `/tmp/sync-docs-intel/` | Running per-batch would re-pay the graph-query cost 13× and produce inconsistent snapshots mid-sync. Single materialization + batch reuse is the intent. |
| I4 | Phase 0.5 Batch 13 catch-all captures anything not matched by Batches 1-12 | New `.md` files land in-scope automatically. Removing the catch-all would silently skip new surfaces — the exact failure mode this sync exists to prevent. |
| I5 | Banned-paths list is the ONLY filter on `git ls-files '*.md'` | Anything else creates implicit coverage holes. A new rules file outside the enumeration would be silently excluded. |
| I6 | `Fact-Pairing:` blocks are MANDATORY; missing pairings fail the per-batch verification grep | The skill's core contract. Without the grep gate, edits can land without citations and the drift-surfacing property degrades silently. |
| I7 | Tier A NEVER edited to match code — the bug is filed on the code | Directional intent (`missions.md §How to use this file`). Weakening Tier A to match drifted code converts the sync from a drift-surfacing tool into a drift-hiding tool. |
| I8 | Shared "Graph-First Verification" block is OUT-OF-LINE, prepended to every batch's ARGS at launch | Embedding it in each batch's objective body risks 13-way drift. Out-of-line composition at launch time means one change propagates to all batches atomically. |
| I9 | Graceful degradation on graph unavailability — annotate, never fail | Graph is additive per `.claude/rules/intelligence.md §Availability`. A graph outage must not block the nightly sync; it must degrade to manual verification with clearly-marked reduced-confidence findings. |
| I10 | `/sync-docs` commits stay on the worktree branch; no push from inside the worktree | User controls when to merge. Pushing from inside the worktree would publish unreviewed changes and bypass the user's merge-time review. |
| I11 | Phase 3 final report is the ONLY user-visible output; batches 1-13 produce NO interim reports | User-visible output mid-sync invites "let me check in on progress" interruptions that break the unattended contract. Final report at the end is the sync's single deliverable. |
| I12 | Every Edit falls into the §"The One-and-a-Half Rule" allowed-categories table; prose rewrites are BANNED even with valid Tier A + Tier B citations | Fact-Pairing catches UN-grounded edits but not GROUNDED-PROSE edits. The 2026-04-19 feedback loop showed sync runs were still landing prose updates despite the Fact-Pairing contract. |
| I13 | `scripts/prose-lint.py` runs as MANDATORY pre-commit gate in Batch Execution Protocol step 5; exit 1 blocks commit | Without a mechanical check, the prose ban relies on reviewer vigilance — the exact failure mode that motivated extracting the rule. The linter's §Exceptions table already handles design-log sidecars; bypassing the linter bypasses the rule. |
| I14 | `plans/**` is IN-SCOPE; lifecycle content (status, checkboxes, HISTORY, task descriptions, success criteria) is BANNED from edits | Plans are the most-consulted planning surface; silent drift (wrong symbol names, outdated spec clauses, broken rule anchors) in plan factual claims degrades every future session's context quality. But plan lifecycle is owned by the plan's author and `/review-plan` — /sync-docs MUST NOT flip checkboxes, rewrite descriptions, or touch `review_pipeline:` markers. Drift touching lifecycle surfaces as `/add-bug`. |
| I15 | `plans/completed/**` + `plans/bug-tracker/**` remain in Banned Paths | Completed plans are a frozen historical record — editing them rewrites history. The bug-tracker has its own lifecycle owned by `/fix-bug` / `/add-bug` / `/review-bugs`. Editing either from /sync-docs is a contract violation. |
| I16 | Phase 0.7 runs EXACTLY ONCE per nightly invocation, BEFORE Phase 1 batch sweep, against EXACTLY ONE focus area | Without the ordering, Phase 0.7 output (path a/b/c) cannot seed Phase 1 batch verification. Without the "exactly once" cap, the semantic phase could consume the whole night. Without "exactly one focus", the analysis becomes an aggregation survey instead of a tiny-step-forward pass. An audit-ledger entry per run IS the enforcement mechanism: no entry = contract violation. |
| I17 | Phase 0.7 produces EXACTLY ONE output per run (path a / b / c / d) | Aggregating multiple gaps into one night defeats the "small nightly change" discipline. Picking the smallest of multiple gaps is mandatory; the other candidates get recorded in the audit entry's "Reasoning" field as deferred, not acted on. |
| I18 | The semantic audit ledger (`.claude/skills/improve-tooling/cmd-sync-docs-semantic-audit.md`) is APPEND-ONLY and exempt from prose-lint | The ledger is sync-internal state analogous to a design-log §4 Lessons section — its value is accumulating prose entries that show the cumulative trajectory. Prose-lint would strip exactly what makes the ledger useful. Retroactive edits to past entries destroy the audit property. |
| I19 | Phase 0.7 path (c) `/create-draft-proposal` is the heavy-path escape hatch, not a casual option | Rule/mission/spec changes are proposal-gated by design (memory: spec-grammar proposal gate). Routing to (c) must be explicitly justified in the audit entry: why (a) and (b) are both insufficient. Casual (c) usage inflates the proposal backlog without producing progress. |
| I20 | Phase 0 MUST force-recreate any stale `.claude/worktrees/sync-docs-YYYY-MM-DD` worktree or branch before `EnterWorktree` | Same-day re-invocation after a crashed / partial / aborted prior run would hit `EnterWorktree` with a conflicting path or branch name and fail. Prior-run scratch has no value (the branch is local-only, never pushed — I10), so discarding it is safe by construction. Scope guarantee: `.claude/worktrees/sync-docs-*` contains only sync-docs scratch; user parallel work lives on `dev`/feature branches, so the generic "never destructive git" ban does not apply to this specific path prefix. |
| I21 | Dev-branch drift during the multi-hour run is EXPECTED; the sync NEVER stops, rebases, fetches, or warns because of it | User parallel work on `dev` does NOT pause for `/sync-docs`. A precondition check comparing worktree HEAD to `origin/dev` would stop the nightly sync the first night the user commits anything during the run — immediate contract violation of the "runs for HOURS unattended" premise. The per-batch Fact-Pairing grep's `git merge-base HEAD origin/dev` is self-consistent inside the linked worktree (shared `.git/refs`) and stays valid regardless of dev drift. Merge-time conflict resolution is the user's problem AFTER Phase 3, not the sync's problem during it. |
| I22 | Snapshot-gap (a file referenced by this skill is ABSENT from the worktree snapshot) is the SAME CLASS of drift as I21; DEGRADE per the Phase 0 Degradation Matrix and CONTINUE | A worktree is a point-in-time snapshot. Files added to `dev` AFTER `EnterWorktree` — including the skill's own dependency files like `missions.md`, `scripts/prose-lint.py`, TPR templates — are legitimately absent from the snapshot. Without an explicit degradation path, the session reaches for the forbidden pause ("structural blocker"), violating the unattended contract. The Degradation Matrix enumerates fallbacks for each mandatory dependency so the sync produces ≥1 meaningful commit even when the snapshot predates skill evolution. 2026-04-19 incident: session paused citing `missions.md` + `prose-lint.py` + TPR template absence as "structural mismatch" despite top-of-file §"Never stop" banner — self-contradicting rationalization ("the contract forbids fetching → I must pause"), which is banned in the new Banned-behaviors list. |

## §4 Lessons from Dogfood / Production Runs

### 2026-04-19 (evening) — Semantic drift analysis (Phase 0.7)

**Context.** User followed up on the morning's prose + plans changes with a deeper reframing: the nightly sync runs for HOURS on unattended wall-clock; spending all of it on mechanical factual-drift correction underuses the budget. The real opportunity is to have the night think deeply — specifically, to ask "is the mission actually realizable in the current code, or is the rule under-specified / the code incomplete?" and produce ONE tiny change that edges toward realization. User-stated example: AIMS rules are complex, code is incomplete/partial — "Does the rules need to be changed to make these a reality to meet the desired mission statement?" Explicit constraint: tiny incremental changes, not big overarching rewrites; the nightly cadence accumulates across days.

**Design chosen.**

- New **Phase 0.7 "Semantic Drift Analysis"** runs AFTER Phase 0.6 Intelligence Pre-Sweep and BEFORE Phase 1 batch sweep. It uses the pre-sweep artifact as its first index, so the expensive graph queries are already materialized.
- Focus-area queue lives **inline in the command file** (user preference: "in the skill"). 12 entries covering the major subsystems. Rotation: `FOCUS_INDEX = $(date +%j) % 12`. Every focus gets a turn every 12 days regardless of which nights run.
- Output menu is **tightest-possible 4 paths** (user preference: "tightest"): (a) factual rule edit (One-and-a-Half Rule compliant); (b) `/add-bug` on code; (c) `/create-draft-proposal` for substantive rule/mission change; (d) no-op with audit entry. Exactly ONE output per run.
- Audit ledger at `.claude/skills/improve-tooling/cmd-sync-docs-semantic-audit.md` — colocated with design log, append-only, prose-lint exempt per I18. Ledger IS the cumulative-progress visibility surface.
- Intent hierarchy preserved: I7 still applies — path (a) cannot weaken a mission to match drifted code; mission/spec change goes to (c) via `/create-draft-proposal`.

**Trade-offs considered.**

- **Scope creep vs. value.** Adding a semantic phase could conflate factual-drift discipline with semantic analysis. Mitigation: Phase 0.7 is structurally separated; its output is ONE artifact, labeled by path; prose-lint still runs on Phase 1 commits; path (a) is held to the same One-and-a-Half Rule as the batch sweeps. The two phases do not interfere.
- **Aggregation temptation.** Big-brain analysis could produce 10 candidate gaps per focus. Mitigation: explicit ONE-output cap + deferred-candidates-field in the audit entry. The discipline is structural, not vibes-based.
- **Heavy path (c) overuse.** `/create-draft-proposal` is expensive; routing too many gaps there inflates the proposal backlog. Mitigation: I19 requires the audit entry to justify why (a) and (b) are both insufficient.
- **Rule edits as prose creep vector.** A "sharpen the rule" output could become prose rationale masquerading as a factual edit. Mitigation: path (a) is strictly One-and-a-Half-Rule-compliant. Rule sharpening that changes behavioral contract routes to (c), not (a).

**What to watch.** First 12 nightly runs will rotate through all focuses once. Expected path distribution: (d) no-op most common (~50-70%), (b) `/add-bug` next (~20-30%), (a) factual-edit occasional (~5-15%), (c) proposal rare (~1-5%). If (d) is near-100%, the semantic phase is too cautious — reviewers should flag. If (c) is >10%, the phase is over-reaching — tighten (c) gating. If the audit ledger shows path (a) producing prose, that's an I12 violation surfacing through a new vector.

### 2026-04-19 — Prose creep + plans coverage gap

**Context.** User invoked `/improve-tooling` with feedback: "Doesn't focus enough on the roadmap and plans, it needs to spend time on these also to make sure they all align with real rules. The goal of this command is small grounded incremental changes every single night. The single most important part of this command by far, beyond everything else is grounded factual changes. I still feel it's doing some prose updates to things that it should definitely not be doing. All changes need to be prescriptive only."

**Three root causes diagnosed.**

1. **Scope gap.** `plans/**` was in Banned Paths with reason "Active work artifacts (own lifecycle)". But plan factual claims (symbol names, crate paths, rule anchors, spec clauses) drift just like any other doc surface — only the lifecycle content (status, checkboxes, HISTORY) is owned by plan/review lifecycle. Blanket-banning `plans/**` meant the most-consulted planning surfaces (roadmap, active plans) never got factually verified, and drift accumulated indefinitely.

2. **Edit-scope gap.** The Fact-Pairing contract (§"The One Rule") enforces that every Edit carries Tier A + Tier B citations. But a well-cited prose rewrite passes the contract — "reword this paragraph for clarity" cites the relevant rule (Tier A) and the current file text (Tier B) and lands despite being banned by global CLAUDE.md §NO PROSE IN AUTHORED .md FILES. Fact-Pairing catches UN-grounded edits, not GROUNDED-PROSE edits. The contract needed an explicit edit-scope taxonomy that enumerates what's allowed.

3. **Enforcement gap.** `scripts/prose-lint.py` exists (added recently for the `/commit-push` flow per global CLAUDE.md) but `/sync-docs` never invoked it. The nightly sync was generating commits that contained prose violations the linter would have flagged. Prose creep bypassed the sync's own quality gate because the gate wasn't wired in.

**Fixes.**

1. Removed `plans/**` from Banned Paths; kept `plans/completed/**` (frozen historical record) and `plans/bug-tracker/**` (owned by `/fix-bug` / `/add-bug` lifecycle).
2. Added new Batch 13 "Roadmap + Active Plans (FACTUAL ALIGNMENT ONLY)" with narrow allowed-edits table (symbol / path / crate / rule-anchor / spec-clause / cross-ref / count / INTENT-ORPHAN-deletion) and explicit banned-edits list (status frontmatter / checkbox state / HISTORY / subsection status / task descriptions / success criteria / prose). Drift touching banned categories files `/add-bug`, never rewrites lifecycle content.
3. Renumbered catch-all to Batch 14; updated all "13"→"14" references across the command.
4. Added "The One-and-a-Half Rule: SCOPE OF ALLOWED EDITS (Factual-Only, Zero Prose)" between "The One Rule" and "The Second Rule" — an allowed-categories table + banned-categories list + pre-commit linter wiring + reviewer-enforcement instructions.
5. Wired `scripts/prose-lint.py` as MANDATORY step 5 in Batch Execution Protocol (was step 5 = commit; commit became step 6). Exit 1 blocks commit; bypass explicitly banned.
6. Prepended SCOPE-OF-ALLOWED-EDITS block to every batch's TPR ARGS alongside GRAPH-FIRST PROTOCOL — reviewers now flag prose edits as CRITICAL.

**What to watch.** First nightly run after these changes will exercise (a) Batch 13 scanning plans + roadmap, (b) the prose-lint gate at every commit, (c) the reviewer-side prose flag. Regressions: Batch 13 touching lifecycle content (CRITICAL — violates I14); a commit landing with prose-lint exit-1 bypassed (CRITICAL — violates I13); prose edits surviving reviewer pass (indicates the prepended SCOPE block didn't propagate — violates I12).

### 2026-04-18 — Autonomous-flag bug + graph-first wiring

**Context.** User invoked `/improve-tooling` with ARGS "I want to make a change to /sync-docs to rely very very heavily on /query-intel, it will instruct the tp agents to use it as well" and then added "Also fix bug where it's not passing the automated or non-interactive flag or whatever we called it ot the /tpr-review command".

**Autonomous-flag root cause.** `/sync-docs` was authored with §Automation Protocol §3 "No `AskUserQuestion` calls" in mind, but the rule applied only to `/sync-docs` itself — not to the `/tpr-review` sub-invocations. `/tpr-review` added an `--autonomous` flag during the 2026-04-17 help-mode refactor, but `/sync-docs` was never updated to pass it. Result: any batch that hit a `/tpr-review §5` cap-exit, §9 transport-failure, or §1 ambiguous-input branch would invoke `AskUserQuestion` mid-nightly and hang forever. The bug is a silent kind — it only manifests when TPR hits an edge case, so morning-after runs that converged cleanly would mask it while the first convergence-failure would strand the sync.

**Fix.** Batch Execution Protocol step 2 now explicitly requires `/tpr-review --autonomous` as the launch form, Automation Protocol step 3 calls out the flag as a MANDATORY contract, and Load-Bearing Invariant I1 above makes it grep-verifiable (`grep -c 'tpr-review --autonomous' .claude/commands/sync-docs.md` should equal the number of launch sites).

**Graph-first root cause.** Pre-refactor, every batch objective told reviewers WHAT to verify against (e.g., `crates/arc/src/`) but not HOW to verify — implicitly licensing manual `cat`/`grep` workflows across 13 batches over hundreds of `.md` files. CLAUDE.md §General Discipline mandates graph-first fact-check but the command didn't enforce it.

**Fix.** Added Phase 0.6 (one-shot materialization), added Graph-First Verification block prepended to every batch's ARGS at launch time (DRY — no per-batch duplication), registered `/sync-docs` as Step F consumer, added Tier B "graph-verified fact" option to Fact-Pairing.

**What to watch.** First real nightly run post-change will either (a) exercise the `--autonomous` path (good — autonomous exits + bug-filing, no hangs) or (b) converge everywhere in interactive-equivalent semantics (also good — just slower validation). If a `/tpr-review` launch in the logs shows missing `--autonomous`, treat as a P0 regression against I1.

## §5 Regressions To Watch For

- [ ] Edit landing in a sync commit that falls OUTSIDE the §"The One-and-a-Half Rule" allowed-categories table — P0. Violates I12. Check: `git log --format=%H <batch-range>` × `git show --stat` — any diff that rewrites a paragraph for clarity/cadence/consistency without a factual correction is a violation. Reviewers must flag as CRITICAL.
- [ ] `scripts/prose-lint.py` bypassed in Batch Execution Protocol step 5 (e.g., `--exit-zero`, skipped call, missing from ARGS) — P0. Violates I13. Grep check: every batch's commit-build sequence in `sync-docs.md` must reference `python3 scripts/prose-lint.py` BEFORE `/commit-push`.
- [ ] Batch 13 edit touching plan lifecycle content (`status:`, checkbox state, `review_pipeline:`, HISTORY block, task description, success criterion) — P0. Violates I14. Reviewers must flag as CRITICAL. Cure: revert the edit, file `/add-bug` subsystem `docs` for the underlying drift.
- [ ] Batch 13 edit to `plans/completed/**` or `plans/bug-tracker/**` — P0. Violates I15. Banned Paths filter should exclude these; any edit landing in these paths means the discovery filter is broken.
- [ ] Nightly run without a Phase 0.7 entry in `cmd-sync-docs-semantic-audit.md` — P0. Violates I16. Grep check: `git log` for the nightly commit should show ≥1 commit matching `docs(sync-docs): semantic audit —` OR the ledger should have an appended entry with today's date.
- [ ] Phase 0.7 producing more than one output (two bug filings, two edits, bug+proposal) — P0. Violates I17. Audit entry shows ONE artifact only; multiple artifacts means aggregation slipped in.
- [ ] Phase 0.7 retroactive ledger edits — P0. Violates I18. `git log -p` on `cmd-sync-docs-semantic-audit.md` must show only appends; modifications to prior dated entries are the pattern to flag.
- [ ] Phase 0.7 path (c) `/create-draft-proposal` chosen without audit-entry justification for why (a) and (b) are insufficient — P1. Violates I19. Audit entry's "Reasoning" field must explicitly rule out (a) and (b).
- [ ] Phase 0.7 running AFTER Phase 1 batches (or in parallel) — P1. Violates I16 ordering. Phase 0.7 output must seed Phase 1 verification; inverting the order breaks the corroboration chain.
- [ ] Focus-area queue drift — a new subsystem (new crate, new rules file) added to the project without a corresponding queue entry — P2. Queue rotates through a fixed 12; new subsystems become invisible to Phase 0.7 until the queue is extended.
- [ ] `/tpr-review` invocation from `/sync-docs` missing `--autonomous` — P0. Grep check: every Skill-tool call site referencing `/tpr-review` in `sync-docs.md` must carry the flag. Any future batch addition or refactor that drops it is a contract violation.
- [ ] Graph-First Verification block inlined into a specific batch's objective body — P1. The block is shared OUT-OF-LINE (§Batch Definitions) per I8. A per-batch inline copy risks 13-way drift where one batch updates and others lag.
- [ ] `/sync-docs` dropped from `compose-intel-summary.md` consumer count or Step F registry — P1. The Registry contract (§Step F) requires consumer-file edits to co-commit the Step F entry. Drift produces `DRIFT:intel-extension-registry` findings in future reviewer cycles.
